# ZE Laser Practice

A browser trainer for CS2 Zombie Escape laser stages and bosses. You spawn where the lasers are and the
**map's own entity logic** runs the stage, 1:1 with a CS2Fixes ZE server (GFL-style). Inspired by
cybo's lasers.cybo.dev, and it writes **his map-folder format** so he can reuse our baked maps.

Read [README.md](README.md) first: the map folder format, scenarios, bosses, the code layout.
[ROADMAP.md](ROADMAP.md) is what's shipped and what's next. Tick boxes as things land, add what you defer.

## Layout

```
bake/        lasers-bake (C#, NuGet ValveResourceFormat 20.1): workshop VPK -> map folder; --panorama; --stock-sounds
web/         the game (Vite + three.js, plain ES modules, no framework)
  src/app/     state, settings, session, loop, input, bosses, endless, records, rules, coop (+ coop-end), voice (V push to talk),
               account (Steam sign-in), replay-* (recording + playback, lib/replay-codec.js)
  src/net/     coop-client.js (the co-op server socket)
  src/ui/      menu, hud, overlay, touch (+ their css)
  src/world/   collision, movement, render, assets, peers (teammates), entities/ (engine + classes/)
  src/audio/   audio.js, voice-* (Opus capture / playback over the co-op socket)
  src/weapons/ viewmodel.js + fp/ (vpkstuff's previewer engine, kept verbatim so fixes can flow both ways)
  src/lib/     shared helpers (dom, math, ...): reuse these, never re-implement them
  server/      co-op server (/coop): coop-relay (rooms, owner rights, public list), coop-round (server-run rounds),
               coop-voice (voice relay), scenarios, activity (feed), api.js (/api/), auth/ (Steam OpenID, session cookie), runs-http.js (solo runs,
               replays, history), db/ (Postgres run store + migrations, memory
               without DATABASE_URL), main.js (standalone); a Vite plugin on dev + preview
  public/scenarios/   hand-written stage definitions (committed)
  public/maps|sounds|panorama|weapons/   generated by the bake / copied assets (gitignored, large, Valve content)
tools/       bake-map.mjs (one-command map bake, BAKING.md), steam.mjs (finds CS2 + workshop), chunk-world.mjs (world
             streaming chunks), io-graph.mjs (scenario authoring), sim.mjs (headless engine), index-maps.mjs
```

## Run

```bash
npm --prefix web install
npm --prefix web run dev            # http://localhost:5804  (.claude/launch.json: "web")
dotnet build bake -c Release        # then see README "Run it locally" for the bake commands
```

## Rules

- **Truth sources, not memory.** "1:1" means the number comes from: the map's own entity data
  (`tools/io-graph.mjs`), CS2's own binaries and files (server.dll / client.dll behaviour, `lasers-bake --panorama`;
  the maintainer's runtime notes, `cs2map/porter/research/docs/07_RUNTIME_SEMANTICS.md`, if you have them),
  CS2Fixes / ZR (github.com/Source2ZE/CS2Fixes `src/`: loadouts, armor, ammo, KeyValue, pushes) and GFL's configs
  (github.com/gflze/CS2-ZE-Configs: bosshud, stripper, mapcfg, entwatch). If the user remembers something different
  from the data, say so with the evidence.
- **No monoliths, no duplicates.** Files stay focused (~100-400 lines). Anything used in two places goes in
  `web/src/lib/` (or the module that owns it) and is imported, never copied. Name things for what they do.
- **Security.** Everything from a map, a scenario, the URL or localStorage is untrusted: escape it before
  `innerHTML` (`lib/dom.js` `esc`), validate names before using them in paths (`lib/paths.js`), never `eval` /
  `new Function` / inline handlers. The bake must never write outside its output folder (VPK paths are
  attacker-controlled: sanitise every path built from them). Keep the CSP in `web/index.html` tight.
- **Never write into the CS2 install.** The old VRF CLI ignores `-o` for `.uifont` and once wrote into
  `game/csgo/panorama/fonts`; use lasers-bake (VRF 20.1) for anything Valve-side.
- **Browser checks: Chrome MCP** (`mcp__claude-in-chrome__*`) against the shared test server `http://localhost:5807`
  (`npm run dev:stable --prefix web`, .claude/launch.json "web-stable"): nothing on it reloads by itself, so other
  sessions' edits never cut a test short; reload the page to pick up edits. Don't test on :5804 (the hot-reloading dev
  server), don't start copies on other ports and don't stop servers other sessions started. If :5807 is down, start it.
  `window.__lasers` is the debug handle: `startScenario(i, mode)`, `pause()` (assigning `.paused` does nothing), `advance(seconds)` (synchronous sim; a hidden
  tab gets no animation frames), `scenarios()`, `engine`, `player`, `run`, `settings`, `audio`, `vm`;
  `window.__lasersInput = (t) => ({forward, side, jump, duck, walk})` drives the player. Tests in the user's Chrome
  are audible: keep the game paused (solo audio is silent while paused; a live round's plays on behind the menu, so
  mute it with `__lasers.audio.setVolumes({ sfx: 0, music: 0 })`) and never leave test values saved in their
  settings (`localStorage['lasers.settings']`).
- **Bash heredocs can mangle backslashes on Windows Git Bash** (`\\` -> `\`): write scripts with the Write tool.
- **Deploy: [deploy/README.md](deploy/README.md).** `git push box main` builds the image on the box (`lasers:latest`,
  log `~/lasers-build.log`); then laser-game is deployed in Helm's UI. A push without the build is invisible to Helm.
- **Commit explicitly** (`git add <files>`, never `-A`), confirm `git diff --cached --name-only` first.
  GitHub repos default **private**; ask before creating or pushing one.
- Platform: built on Windows (PowerShell + Git Bash). CS2 and its workshop maps are found from Steam's library list
  (`node tools/steam.mjs` prints them; override with `LASERS_CS2` / `LASERS_WORKSHOP`). A fresh checkout has no maps:
  BAKING.md "From a fresh checkout" bakes them from your own CS2 (`node tools/bake-map.mjs --scenarios`).
